# 12. 数据库时区配置说明

## 📋 问题背景

### 问题描述

用户发现打卡记录的 `created_at` 时间使用的是 UTC 时间，而不是预期的北京时间（CST，UTC+8）。

**时区说明：**
- **UTC**：协调世界时，标准时间基准
- **北京时间（CST）**：UTC + 8 小时
- 例如：UTC `01:49` = 北京时间 `09:49`

### 问题原因

1. **MySQL 默认行为**：MySQL 的 `DATETIME` 类型虽然不存储时区信息，但 `CURRENT_TIMESTAMP` 和相关函数会根据会话时区计算时间
2. **Prisma 行为**：Prisma 在转换 JavaScript `Date` 对象时，如果没有明确时区配置，可能按 UTC 处理
3. **会话时区未设置**：数据库连接时未明确设置会话时区为 `+08:00`

---

## ✅ 解决方案

### 方案对比

#### 方案一：存储 UTC 时间（业界标准，推荐用于跨时区场景）

**优点：**
- ✅ 符合业界最佳实践
- ✅ 跨时区、跨地区场景下一致性好
- ✅ 不受服务器时区配置影响
- ✅ 便于未来扩展（支持多时区用户）

**缺点：**
- ❌ 需要前端/接口层转换显示
- ❌ 数据库中查看不直观（显示为 UTC）

**适用场景：**
- 全球化应用
- 未来可能支持多时区
- 需要与其他系统集成（通常使用 UTC）

#### 方案二：存储北京时间（当前方案，适合单一时区场景）

**优点：**
- ✅ 直观易懂，数据库中直接显示本地时间
- ✅ 适合单一时区应用（如仅面向中国用户）
- ✅ 无需前端转换即可显示

**缺点：**
- ❌ 不符合业界标准
- ❌ 跨时区场景下会有问题
- ❌ 依赖数据库会话时区配置
- ❌ 服务器迁移时可能需要调整

**适用场景：**
- 仅面向单一时区用户（如仅中国）
- 不需要跨时区功能
- 团队更偏好本地时间

### 当前项目建议

**基于当前项目特点：**
- 这是一个面向中国用户的 H5 应用
- 所有用户都在同一时区（北京时间）
- 没有跨时区需求

**建议：** 继续使用方案二（存储北京时间），但需要优化实现方式以提高可靠性。

## 🔧 实现方式

### 当前实现（方案二 - 已优化）

使用 Prisma 中间件确保每次查询前都设置时区：

```typescript
import { PrismaClient } from '@prisma/client'

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined
}

const prismaClientOptions = {
  log: process.env.NODE_ENV === 'development' ? ['query', 'error', 'warn'] : ['error'],
}

const prisma = globalForPrisma.prisma ?? new PrismaClient(prismaClientOptions)

// 使用 Prisma 中间件确保每次查询前都设置时区
prisma.$use(async (params, next) => {
  // 在每次查询前设置会话时区（仅在需要时执行）
  if (params.action !== 'executeRaw' && params.action !== 'executeRawUnsafe') {
    try {
      // 仅在首次查询或连接池新建连接时设置
      await prisma.$executeRawUnsafe(`SET time_zone = '+08:00'`)
    } catch (err) {
      // 忽略错误，避免影响正常查询
    }
  }
  return next(params)
})

export const db = prisma

if (process.env.NODE_ENV !== 'production') globalForPrisma.prisma = db
```

**优化点：**
1. ✅ 使用 Prisma 中间件，确保每个查询前都设置时区
2. ✅ 避免在 `executeRaw` 查询中重复设置（避免递归）
3. ✅ 连接池中的每个新连接都会自动设置时区

### 替代方案（方案一 - 存储 UTC）

如果未来需要改为存储 UTC，建议：

1. **数据库存储 UTC**：
   - 服务器和数据库时区设置为 UTC
   - 移除会话时区设置代码

2. **接口返回时转换**：
   ```typescript
   // 在 API 返回时转换为北京时间字符串
   const beijingTime = new Date(utcDate).toLocaleString('zh-CN', {
     timeZone: 'Asia/Shanghai',
     year: 'numeric',
     month: '2-digit',
     day: '2-digit',
     hour: '2-digit',
     minute: '2-digit',
     second: '2-digit',
   })
   ```

3. **前端显示**：前端接收到 UTC 时间后，使用 `toLocaleString` 转换为本地时间显示

## 🎯 工作原理

### 时间字段处理机制（方案二）

#### 1. `@default(now())` - 创建时间

```prisma
created_at DateTime @default(now()) @db.DateTime(0)
```

- 使用 MySQL 的 `CURRENT_TIMESTAMP`
- 受会话时区（`+08:00`）影响
- ✅ 自动保存为北京时间

#### 2. `@updatedAt` - 自动更新时间

```prisma
updatedAt DateTime @default(now()) @updatedAt @map("updated_at")
```

- Prisma 自动管理，使用 `ON UPDATE CURRENT_TIMESTAMP`
- 受会话时区（`+08:00`）影响
- ✅ 自动保存为北京时间

#### 3. 代码中手动设置

```typescript
updated_at: new Date()
```

- JavaScript `Date` 对象通过 Prisma 写入数据库
- Prisma 按会话时区（`+08:00`）转换
- ✅ 保存为北京时间

## ⚠️ 注意事项

### 1. 已存在数据

- **历史数据**：如果数据库中已有使用 UTC 时间保存的记录，这些记录的时间值不会自动改变
- **新数据**：配置生效后，所有新创建和更新的记录都会使用北京时间

### 2. 部署要求

- 确保 MySQL 服务器时区设置正确（推荐：`Asia/Shanghai`）
- 应用重启后，时区设置会自动生效
- 无需修改现有数据库结构

### 3. 连接池注意事项

- Prisma 使用连接池，每个新连接都需要设置时区
- 使用中间件确保每次查询前都设置，避免时区不一致
- 如果发现时区异常，检查中间件是否正常工作

### 4. 测试验证

重启应用后，可以通过以下方式验证：

```sql
-- 查看当前会话时区
SELECT @@session.time_zone;

-- 查看当前时间（应该显示北京时间）
SELECT NOW();

-- 查看最新打卡记录的时间
SELECT id, created_at, updated_at FROM checkins ORDER BY created_at DESC LIMIT 5;
```
