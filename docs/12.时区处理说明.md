# 12. 时区处理说明

## 📋 概述

本文档说明系统中时区的处理方式，包括数据存储、结算逻辑、时间展示和服务器配置。

---

## 🎯 核心原则

### 设计理念

1. **数据库存储 UTC 时间**：符合业界标准，避免时区问题
2. **业务逻辑基于北京时间**：所有周编号计算、结算逻辑都基于北京时间
3. **展示时自动转换**：前端和服务端展示时自动转换为北京时间

---

## 💾 数据存储（UTC 时间）

### 存储方式

所有时间字段（`created_at`、`updated_at` 等）都以 **UTC 时间** 存储到数据库。

**实现方式：**
- 使用 Prisma ORM，不设置数据库会话时区
- JavaScript `Date` 对象自动转换为 UTC 时间存储
- MySQL `DATETIME` 类型存储 UTC 时间

**示例：**
```typescript
// 用户在北京时间周一凌晨 2:00 打卡
const beijingTime = new Date('2026-01-20T02:00:00+08:00')

// 保存到数据库
await db.checkins.create({
  data: {
    created_at: beijingTime,  // 自动转换为 UTC: 2026-01-19T18:00:00Z
    week_number: 202604,      // 基于北京时间计算
  },
})
```

**数据库中的实际值：**
- `created_at`: `2026-01-19T18:00:00.000Z` (UTC 时间，周日 18:00)
- `week_number`: `202604` (基于北京时间计算)

## 🔢 周编号计算（基于北京时间）

### 关键设计

**周编号（`week_number`）是查询和结算的核心依据，而不是时间字段。**

### 计算逻辑

1. **打卡时计算周编号**
   ```typescript
   // app/api/checkin/route.ts
   const mockDate = getCurrentDate(request.headers)  // 获取当前时间（支持模拟时间）
   const weekNumber = getWeekNumber(mockDate)        // 基于北京时间计算周编号
   ```

2. **周编号计算函数**
   ```typescript
   // lib/week.ts
   export function getWeekNumber(date?: Date): number {
     // 找到该日期所在周的周一（基于服务器本地时区）
     const monday = getMonday(date)
     // 计算周编号：YYYYWW 格式（如 202604）
     return year * 100 + week
   }
   ```

3. **依赖服务器时区**
   - 如果服务器时区是 `Asia/Shanghai`，`getWeekNumber()` 会基于北京时间计算
   - 如果服务器时区不是 `Asia/Shanghai`，计算结果可能不准确
   - **建议：确保服务器时区设置为 `Asia/Shanghai`**

### 为什么使用周编号而不是时间字段？

**优势：**
- ✅ 避免时区转换问题
- ✅ 查询简单高效（直接查询 `week_number` 字段）
- ✅ 不受 UTC 时间影响

**示例：**
```typescript
// 用户在北京时间周一凌晨 2:00 打卡
// UTC 时间是周日 18:00，但 week_number 是 202604（本周）

// 结算时查询
const checkins = await db.checkins.findMany({
  where: { week_number: 202604 }  // 直接查询周编号，不依赖时间字段
})
// ✅ 能正确找到记录，即使 created_at 是 UTC 时间（周日 18:00）
```

## 📊 结算逻辑

### 结算流程

1. **计算当前周编号**
   ```typescript
   // lib/settlement.ts
   const weekNumber = getWeekNumber()  // 基于服务器时区（应该是北京时间）
   ```

2. **查询打卡记录**
   ```typescript
   // 查询本周所有打卡记录（使用 week_number，不依赖时间字段）
   const currentCheckins = await db.checkins.findMany({
     where: { week_number: weekNumber }
   })
   ```

3. **排序规则**
   ```typescript
   // 按 weightDiff 降序，如果相同则按打卡时间升序
   eligibleUsers.sort((a, b) => {
     if (b.weightDiff !== a.weightDiff) {
       return b.weightDiff - a.weightDiff
     }
     // 使用 created_at 作为排序依据（UTC 时间，但排序结果正确）
     return a.checkinTime.getTime() - b.checkinTime.getTime()
   })
   ```

### 定时结算

```typescript
// lib/settlement.ts
cron.schedule(
  '0 21 * * 1',  // 每周一 21:00
  async () => {
    const weekNumber = getWeekNumber()
    await settleWeekRanking(weekNumber)
  },
  {
    timezone: 'Asia/Shanghai',  // 明确指定时区为北京时间
  }
)
```

**注意：**
- 定时任务使用 `Asia/Shanghai` 时区
- 结算时计算的周编号基于服务器时区（应该是北京时间）
- 查询使用 `week_number` 字段，不依赖 `created_at` 时间

## 🖥️ 时间展示（自动转换）

### 服务端 API 返回

**实现方式：**
```typescript
// app/api/user/checkins/route.ts
date: new Date(checkin.created_at).toLocaleDateString('zh-CN', {
  year: 'numeric',
  month: '2-digit',
  day: '2-digit',
})
```

**转换逻辑：**
- `checkin.created_at` 是 UTC 时间（如 `2026-01-19T18:00:00Z`）
- `new Date()` 创建 Date 对象
- `toLocaleDateString('zh-CN')` 转换为本地时区显示
- 如果服务器时区是 `Asia/Shanghai`，会自动转换为北京时间

**示例：**
```typescript
// 数据库中的 UTC 时间
const utcTime = new Date('2026-01-19T18:00:00.000Z')

// 转换为显示格式
const displayDate = utcTime.toLocaleDateString('zh-CN', {
  year: 'numeric',
  month: '2-digit',
  day: '2-digit',
})
// 结果：'2026/01/20'（如果服务器时区是 Asia/Shanghai）
```

### 前端显示

前端接收到的时间数据：
- `createdAt`: UTC 时间的 Date 对象（如 `2026-01-19T18:00:00.000Z`）
- `date`: 已格式化的日期字符串（如 `'2026/01/20'`）

前端可以直接使用 `date` 字段显示，或使用 `createdAt` 自行格式化。

## 🖥️ 服务器时区配置

### 要求

**服务器时区必须设置为 `Asia/Shanghai`（北京时间）**

### 原因

1. **周编号计算依赖服务器时区**
   - `getWeekNumber()` 使用 `new Date()` 和 `getDay()` 等方法
   - 这些方法基于服务器本地时区计算
   - 如果服务器时区不是 `Asia/Shanghai`，周编号计算可能错误

2. **时间展示依赖服务器时区**
   - `toLocaleDateString()` 使用服务器本地时区
   - 如果服务器时区不是 `Asia/Shanghai`，显示时间可能不正确

### 配置方式

#### Docker 容器（推荐方式）

**在 docker-compose.yml 中配置时区环境变量**

对于 Node.js 应用，只需要设置 `TZ` 环境变量即可，Node.js 会自动识别并使用该时区。

```yaml
# docker-compose.yml
services:
  app:
    environment:
      - TZ=Asia/Shanghai  # 添加这一行
      - DATABASE_URL=...
      # ... 其他环境变量
```

**配置后重启容器：**
```bash
docker-compose restart app
```

**验证配置：**
```bash
# 检查容器内 Node.js 时区
docker exec <container-name> node -e "console.log(Intl.DateTimeFormat().resolvedOptions().timeZone)"
# 应该输出: Asia/Shanghai
```

**为什么只需要环境变量？**
- ✅ Node.js 会读取 `TZ` 环境变量
- ✅ `getDay()`、`toLocaleString()` 等方法会基于 TZ 环境变量计算
- ✅ 不需要修改 Dockerfile 或安装 tzdata
- ✅ 重启容器即可生效，无需重新构建镜像

**不配置时区的风险：**
- ❌ 容器默认使用 UTC 时区
- ❌ 周编号计算可能错误
- ❌ 时间展示可能不正确
- ❌ 不同部署环境可能行为不一致

#### 云服务器

```bash
# 设置时区
sudo timedatectl set-timezone Asia/Shanghai

# 验证
timedatectl
```

**注意：** 
- 云服务器时区设置为 `Asia/Shanghai` 是推荐的，但不是必须的
- **Docker 容器必须**在 `docker-compose.yml` 中配置 `TZ=Asia/Shanghai` 环境变量
- 容器时区配置独立于宿主机时区，不会自动继承

## 📝 时间字段使用场景

### `created_at` 字段用途

1. **排序**：按时间排序记录
   ```typescript
   orderBy: { created_at: 'desc' }
   ```

2. **显示**：在前端显示打卡日期
   ```typescript
   date: new Date(checkin.created_at).toLocaleDateString('zh-CN', {...})
   ```

3. **统计**：计算时间范围和数据
   ```typescript
   const sorted = checkins.sort((a, b) => 
     a.created_at.getTime() - b.created_at.getTime()
   )
   ```

4. **结算排序**：当 `weightDiff` 相同时，按打卡时间排序
   ```typescript
   return a.checkinTime.getTime() - b.checkinTime.getTime()
   ```

**注意：`created_at` 不用于查询条件，查询使用 `week_number` 字段。**

## ⚠️ 注意事项

### 1. 服务器时区要求

**必须确保服务器时区是 `Asia/Shanghai`**，否则：
- ❌ 周编号计算可能错误
- ❌ 时间展示可能不正确
- ❌ 结算可能查询不到正确的记录

**Docker 容器时区说明：**
- 容器默认使用 UTC 时区，**不会**自动继承宿主机时区
- **必须**在 `docker-compose.yml` 中明确配置 `TZ=Asia/Shanghai` 环境变量
- 对于 Node.js 应用，只需要设置环境变量即可，无需修改 Dockerfile
- 配置后重启容器即可生效，无需重新构建镜像

### 2. 时区转换

- 数据库存储的是 UTC 时间
- 展示时自动转换为服务器本地时区（应该是北京时间）
- 如果服务器时区不是 `Asia/Shanghai`，需要手动指定时区转换

### 3. 跨时区访问

- 如果用户在不同时区访问，前端显示的时间可能不同
- 建议前端也使用 `toLocaleString()` 并指定 `timeZone: 'Asia/Shanghai'`
